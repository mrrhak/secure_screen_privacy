## Project status

This started as a Flutter plugin scaffold generated by `flutter create --template=plugin --platforms=android,ios` (plugin name `secure_screen_privacy`, Android package `com.mrrhak.secure_screen_privacy`) and now implements two real features:

- **Capture protection** (`enableCaptureProtection`/`disableCaptureProtection`/`isCaptureProtectionEnabled`) — blocks screenshots and screen recording for as long as it's enabled, via Android `WindowManager.LayoutParams.FLAG_SECURE` and an iOS "secure `UITextField`" window-reparenting trick.
- **App switcher protection** (`enableAppSwitcherProtection`/`disableAppSwitcherProtection`/`isAppSwitcherProtectionEnabled`) — on iOS, shows a blur/image/color overlay (`AppSwitcherProtectionMode`) in the OS App Switcher preview instead of live content, applied via `applicationWillResignActive`/`sceneWillResignActive` + `didBecomeActive` hooks. iOS's `blur`/`imageBlur` modes render the blur with a synchronous `UIVisualEffectView`/`UIBlurEffect` (selected from the Dart-facing `BlurIntensity` enum — `ultraLight`/`light`/`medium`/`heavy`, default `ultraLight` — via a pure `blurStyle(forIntensity:)` mapping into `.systemUltraThinMaterial`/`.systemThinMaterial`/`.systemMaterial`/`.systemThickMaterial` respectively), attached in the same synchronous step as `color`/`image` mode's overlay — not a manually-captured-and-`CIGaussianBlur`-processed bitmap, which was the original approach. That bitmap approach required the actual blur computation to happen asynchronously off the main thread, meaning the blurred replacement content could attach to the window *after* `willResignActive`/`sceneWillResignActive` had already returned — the same point at which the OS can capture the App Switcher snapshot — creating a race where the snapshot could be taken before the overlay was in place. `UIVisualEffectView` sidesteps this because it attaches synchronously like the other three modes, with no async round trip to race against. `BlurIntensity` replaced an earlier continuous `blurRadius: double` parameter that a pure `blurStyle(forRadius:)` function bucketed into the same styles by radius range, deliberately excluding `.systemThickMaterial`: Apple's thicker/more-opaque materials are designed for toolbars/sidebars needing solid text legibility (confirmed via on-device testing), so on an auto-scaled continuum that tier read as a near-flat, barely-blurred regression rather than the strongest step. Once blur intensity became a discrete, developer-chosen enum instead of an implicit radius bucket, that ambiguity disappeared — `heavy`/`.systemThickMaterial` is now a legitimate, deliberately-selected top tier, so all four materials are exposed. `BlurIntensity`'s value names are deliberately platform-neutral (not `UIBlurEffect.Style` names) so a future Android blur implementation could reuse the same enum. On Android, there is no custom overlay at all: `enableAppSwitcherProtection` simply forces `WindowManager.LayoutParams.FLAG_SECURE` on for the Activity's window and leaves it on for the entire time protection is enabled (mirroring `enableCaptureProtection`'s own flag, and reapplied on Activity recreation alongside it), regardless of which `AppSwitcherProtectionMode` was requested. `mode`/`blurIntensity`/`color`/`imageBackgroundColor` are still accepted on the Android method channel for cross-platform API-contract parity with iOS, but are otherwise unused there. This design followed direct testing (confirmed on a real device, Samsung SM-J810Y, Android 10/API 29, gesture nav enabled) that established two things: (1) a genuinely-backgrounded task's cached recents snapshot only reflects view content whose final state is set *synchronously*, before/at the first render after pause — meaning a custom overlay view can look right for the settled/discrete case, but any asynchronous or live-compositor rendering (a `RenderEffect` blur, or a `PixelCopy`-captured-and-blurred bitmap) reliably does **not** make it into that snapshot; and (2) **no technique at all** — custom overlay, `RenderEffect`, `PixelCopy`, or even `FLAG_SECURE` itself — hides content during the live "swipe up and hold" gesture-nav peek specifically, because during that hold Android/OneUI's "live tile" recents preview composites the app's actual on-screen window directly (most likely mirroring `FlutterSurfaceView`'s own SurfaceFlinger layer), which is real-time primary-display rendering rather than a capture/cast/recording. Since `FLAG_SECURE` alone already covers everything Android *can* protect (the settled/discrete case — verified via adb across full backgrounding, a direct app-switch peek, and revisiting a cached thumbnail after switching to a different app) and nothing closes the live-hold-peek gap, the custom overlay/blur machinery was removed as pure added complexity with no corresponding protection benefit. **This live-hold-peek gap remains an unfixed, known Android limitation** — no app-level fix exists for it. iOS is unaffected (its secure-window mechanism has no equivalent live-compositor bypass) and keeps its full set of custom overlay `AppSwitcherProtectionMode` renderings.
- **Screenshot detection** (`screenshotEvents`, a `Stream<ScreenshotEvent>`) — reports screenshots as they happen. Backed by a dedicated `EventChannel('secure_screen_privacy/screenshot_events')`, separate from the `MethodChannel`; subscribing to the stream is what starts native detection and cancelling stops it (no separate start/stop method), via the `EventChannel.StreamHandler` `onListen`/`onCancel` pair (Android) and the equivalent `FlutterStreamHandler` conformance (iOS). Payload is timestamp-only, no file path — deliberately, so no Android storage/media permission is ever requested (`AndroidManifest.xml` stays empty), and because iOS's notification never carries a path anyway. On Android, a `ContentObserver` watches `MediaStore.Images.Media.EXTERNAL_CONTENT_URI` (registered against the engine-scoped `appContext`, not tied to Activity attach state, since a screenshot is a device-level event); its `onChange` runs on a dedicated `HandlerThread` and best-effort queries `DISPLAY_NAME`/`RELATIVE_PATH` (or `DATA` pre-API 29) plus `DATE_ADDED`, then feeds them to the pure top-level function `shouldEmitScreenshotEvent` to decide whether to emit — this is a deliberate improvement over the sibling `no_screenshot` plugin, which treats *any* `MediaStore.Images` change as a screenshot with no filtering at all. The filter matches on a "screenshot" substring in the path/name plus recency, but **fails open** (still emits) whenever the metadata is inconclusive (query failed, columns unavailable) rather than silently dropping a real screenshot — a missed screenshot defeats the point of the feature, while an occasional false positive (e.g. a saved photo) does not. This means the filter can both under-report (non-English locales where the display name is localized, e.g. "Bildschirmfoto") and over-report (inconclusive metadata) depending on locale/OEM — not confirmed across real hardware/OEM variance. On iOS, `UIApplication.userDidTakeScreenshotNotification` is observed via `NotificationCenter`; delivery to `FlutterEventSink` is wrapped in `DispatchQueue.main.async` defensively since Apple doesn't document that notification as guaranteed main-thread. Neither platform scopes detection to "this app's UI was visible" — both fire for any screenshot taken anywhere while a subscription is active (Android: MediaStore-wide; iOS: process-wide notification) — and neither de-duplicates a platform signal that fires more than once for one screenshot. The `ContentObserver`/`HandlerThread` wiring itself (as opposed to the pure `shouldEmitScreenshotEvent` filter) is not covered by this repo's Android unit tests — this project's plain-JUnit setup runs against the stub `android.jar` with no Robolectric, where real framework calls like `MediaStore.Images.Media.EXTERNAL_CONTENT_URI` (which touches `Uri.parse` internally) or constructing a real `Looper`/`HandlerThread` throw/misbehave rather than doing anything, so that wiring is manual/example-app-verified only, the same class of gap already accepted for the screen-recording-callback registration wiring below.
- **Screen recording detection** (`screenRecordingEvents`, a `Stream<ScreenRecordingEvent>`) — reports screen recording/mirroring start and stop. Backed by a third channel, `EventChannel('secure_screen_privacy/screen_recording_events')`, subscribe-starts/cancel-stops just like `screenshotEvents`. **Architectural difference from `screenshotEvents`**: both Android detection APIs are Activity-scoped (`act.windowManager`/`act.mainExecutor` need a live `Activity`), unlike the engine-scoped screenshot `ContentObserver` — so this feature threads an `isRecordingListening` flag (set in `onListen`/cleared in `onCancel`, not a separate method call) through the existing `ActivityAware` callbacks: `onAttachedToActivity`/`onReattachedToActivityForConfigChanges` (re-)register against the newly-attached Activity if the flag is set, `onDetachedFromActivityForConfigChanges`/`onDetachedFromActivity` unconditionally unregister (before `activity = null`, since the unregister path reads `activity` itself), mirroring the sibling `no_screenshot` plugin's own `isRecordingListening`-gated pattern exactly. Android has three SDK-gated tiers, selected by the pure top-level function `screenRecordingRegistrationPathForSdkInt`: **API 35+** uses `WindowManager.addScreenRecordingCallback(Executor, Consumer<Int>)`, giving true start *and* stop detection (state compared against `WindowManager.SCREEN_RECORDING_STATE_VISIBLE` via the pure `isRecordingStateVisible`) — its return value also synchronously reports the *current* state, so a late subscriber isn't left waiting for the next transition. **API 34** uses `Activity.registerScreenCaptureCallback`, which only fires once when recording *starts* — there is no OS-level stop callback at all on this API in isolation, so `isRecording` is only ever emitted `true`; matching `no_screenshot`'s behavior exactly, the only way to reset it is for the Dart subscriber to cancel and re-subscribe. A further wrinkle: if a config change recreates the Activity while a recording is already active on this API tier specifically, the plugin won't re-signal `true` after recreation, since (unlike the API 35+ path) `registerScreenCaptureCallback` has no synchronous initial-state query — an OS API limitation, not something worked around. **Below API 34**: graceful no-op, nothing is ever emitted; minSdk stays 24 (this is purely a runtime `Build.VERSION.SDK_INT` guard). On iOS, `UIScreen.capturedDidChangeNotification` is observed via `NotificationCenter`; because `.isCaptured` is a live boolean re-read on every firing rather than a directional event, one observer correctly reports both start and stop with no "stuck true" problem — reads `activeWindow()?.windowScene?.screen.isCaptured`, falling back to the first connected scene if `onListen` fires before any scene is foreground-active. Neither platform requires a permission. **Reusable pattern worth noting for any future third stream feature**: a single `EventChannel.StreamHandler`/`FlutterStreamHandler` instance registered against two different channels cannot tell which channel invoked `onListen`/`onCancel` (`arguments` is only the Dart-side `listen()` payload, never the channel name) — so this channel gets its *own* dedicated handler rather than reusing the plugin class's existing screenshot handler: an anonymous `object : EventChannel.StreamHandler` on Android (closes over the outer instance for free), and a small dedicated `ScreenRecordingStreamHandler: NSObject, FlutterStreamHandler` class on iOS (holding a `weak var plugin` back-reference, with the plugin itself holding the strong reference so its lifetime is explicit).

Expect to touch all three layers (Dart API, Android, iOS) in tandem when adding to either feature, and update this Architecture section when adding a new one.

## Commands

Run all commands from the repo root unless noted.

- Install deps: `flutter pub get` (and `cd example && flutter pub get` for the example app)
- Analyze/lint: `flutter analyze`
- Run all Dart tests: `flutter test`
- Run a single Dart test: `flutter test test/secure_screen_privacy_test.dart`
- Run Android native unit tests: `cd android && ./gradlew test` (or open `android/` in Android Studio)
- Run the example app: `cd example && flutter run`
- Run integration test on a device/emulator: `cd example && flutter test integration_test/plugin_integration_test.dart`

## Architecture

Standard Flutter federated-plugin layout, split into a platform-agnostic Dart API and per-platform native implementations connected by a single `MethodChannel`:

- `lib/secure_screen_privacy.dart` — public Dart API that app code calls; delegates to `SecureScreenPrivacyPlatform.instance`. Exports `AppSwitcherProtectionMode` (`lib/app_switcher_protection_mode.dart`), `BlurIntensity` (`lib/blur_intensity.dart`), `ScreenshotEvent` (`lib/screenshot_event.dart`), and `ScreenRecordingEvent` (`lib/screen_recording_event.dart`) so a single import is enough.
- `lib/secure_screen_privacy_platform_interface.dart` — abstract `PlatformInterface` defining the contract all platform implementations must satisfy. Uses the `PlatformInterface` token pattern to prevent invalid overrides — any new platform implementation must extend this class and call `PlatformInterface.verifyToken`.
- `lib/secure_screen_privacy_method_channel.dart` — default implementation using `MethodChannel('secure_screen_privacy')`; this is what `platform_interface.dart` uses unless overridden (e.g. by a federated platform package).
- `android/src/main/kotlin/.../SecureScreenPrivacyPlugin.kt` — Android side of the method channel, registered via `FlutterPlugin`; method names dispatched in `onMethodCall`. App switcher protection has no rendering of its own on this platform — `enableAppSwitcherProtection`/`disableAppSwitcherProtection` just toggle `WindowManager.LayoutParams.FLAG_SECURE` on the Activity's window, sharing the same reapply-on-Activity-recreation logic as `enableCaptureProtection`'s own flag (see the App switcher protection bullet above for why Android has no custom overlay). Also implements `EventChannel.StreamHandler` for the screenshot-event stream — see the "Screenshot detection" bullet above for `onListen`/`onCancel`, the `ContentObserver`, and the `shouldEmitScreenshotEvent` filter. The screen-recording-event stream gets its own dedicated `EventChannel.StreamHandler` object (not `this`) registered against a separate channel in `onAttachedToEngine`, plus `isRecordingListening`-gated (re-)registration wired through the `ActivityAware` callbacks — see the "Screen recording detection" bullet above.
- `ios/secure_screen_privacy/Sources/secure_screen_privacy/SecureScreenPrivacyPlugin.swift` — iOS side (Swift Package Manager plugin layout, not CocoaPods-only), registered via `FlutterPlugin`. Image mode loads `UIImage(named: "SecureScreenPrivacyImage")` from the host app's asset catalog, validated at `enableAppSwitcherProtection` time (returns `false` if missing) rather than lazily at overlay-show time. Also implements `FlutterStreamHandler` for the screenshot-event stream, observing `UIApplication.userDidTakeScreenshotNotification` — see the "Screenshot detection" bullet above. The screen-recording-event stream is handled by a separate `ScreenRecordingStreamHandler` class defined at the bottom of this file (see the "Screen recording detection" bullet above for why it can't share the plugin's own screenshot handler).
- `example/` — standalone Flutter app depending on the plugin via a `path: ../` dependency; used both for manual testing (`flutter run`) and integration tests.
- `lib/secure_route_config.dart` + `lib/secure_screen_privacy_navigator_observer.dart` — pure-Dart convenience layer built entirely on top of the public API above (`SecureScreenPrivacyNavigatorObserver` calls `enableCaptureProtection`/`enableAppSwitcherProtection`/etc. per route); no native code involved, so changes here never touch Android/iOS.

When adding a new plugin method: add it to the abstract platform interface, implement it in the method channel class, then implement the native handler on each platform (`onMethodCall` switch on Android, `switch call.method` on iOS), matching the method channel name (`secure_screen_privacy`) and method name exactly across all four files. For a push-based (stream) feature instead of a request/response method, use a separate, namespaced `EventChannel('secure_screen_privacy/<feature>')` rather than overloading the single `MethodChannel` — see `screenshotEvents`/`secure_screen_privacy/screenshot_events` for the pattern: `EventChannel.StreamHandler` (Android) / `FlutterStreamHandler` (iOS) `onListen`/`onCancel` starts/stops the native work, so there's no separate start/stop method call needed. **If adding a second (or third) stream channel**: give it its own dedicated `StreamHandler`/`FlutterStreamHandler` object rather than reusing an existing one — a single handler instance registered against two channels cannot tell which channel invoked `onListen`/`onCancel`, so sharing one is incorrect, not just untidy (see `screenRecordingEvents`' `ScreenRecordingStreamHandler` on iOS and its anonymous `object : EventChannel.StreamHandler` on Android for the pattern).

Test coverage mirrors this structure: `test/secure_screen_privacy_test.dart` tests the public Dart API against a mock `SecureScreenPrivacyPlatform`, `test/secure_screen_privacy_method_channel_test.dart` tests the method channel implementation directly (using `setMockStreamHandler` for `EventChannel`-backed features), and `android/src/test/kotlin/.../SecureScreenPrivacyPluginTest.kt` tests the Android native handler. Where native logic depends on real Android framework behavior this plain-JUnit setup can't safely exercise (no Robolectric) — e.g. `MediaStore`/`Uri`/`Looper` for screenshot detection, `WindowManager`/`Activity` screen-recording-callback registration — extract the decision logic into a pure, Android-framework-free top-level function (see `shouldEmitScreenshotEvent`, `screenRecordingRegistrationPathForSdkInt`, `isRecordingStateVisible`) and unit-test that directly instead; the actual registration/callback wiring for all of these is intentionally left to manual/example-app verification only.
