# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

This started as a Flutter plugin scaffold generated by `flutter create --template=plugin --platforms=android,ios` (plugin name `secure_screen_privacy`, Android package `com.mrrhak.secure_screen_privacy`) and now implements two real features:

- **Capture protection** (`enableCaptureProtection`/`disableCaptureProtection`/`isCaptureProtectionEnabled`) — blocks screenshots and screen recording for as long as it's enabled, via Android `WindowManager.LayoutParams.FLAG_SECURE` and an iOS "secure `UITextField`" window-reparenting trick. On iOS the window to protect is the plugin's own engine window (`ownWindowProvider`, set in `register(with:)` to `registrar.viewController?.view.window`), falling back to the foreground-active scene's key window (`activeWindow()`) only while that is nil; it's re-picked on every enable and become-active. This matters on iPad multi-window, where each window runs its own engine and plugin instance: picking the active scene let one instance protect another window and leave its own open (seen with two real scenes on an iPad simulator; `RunnerTests` covers it with stand-in windows). Only *enabling* reparents the window (`attachWindowIfNeeded`); `disableCaptureProtection` just turns the secure field off if a window is already attached, so an app that never enables protection never has its window moved (tested in `RunnerTests` via `isWindowAttachedToSecureField`). **Background snapshot (iOS):** the snapshot iOS saves when the app enters the background (what the App Switcher shows after pressing Home) treats the secure layer like any capture, so with capture protection on and app switcher protection off it came out all black, while the live App Switcher opened straight from the app looked normal. `handleDidEnterBackground` (`sceneDidEnterBackground`/`applicationDidEnterBackground`) switches the secure field off for the protected window's scene in that case, and `handleWillEnterForeground` (`sceneWillEnterForeground`/`applicationWillEnterForeground`) switches it back on before the window returns, unless the app switcher overlay still covers it (then `handleDidBecomeActive` does it, as before). With app switcher protection on, the overlay path handles the snapshot and the background hook does nothing. Checked on an iOS 27.2 simulator via the saved SplashBoard snapshot; `simctl io screenshot` ignores the secure layer, so it can't show foreground protection.
- **App switcher protection** (`enableAppSwitcherProtection`/`disableAppSwitcherProtection`/`isAppSwitcherProtectionEnabled`) — on iOS, shows a blur/image/color overlay (`AppSwitcherProtectionMode`) in the OS App Switcher preview instead of live content, applied via `applicationWillResignActive`/`sceneWillResignActive` + `didBecomeActive` hooks. The window(s) to cover come from the callback's own `UIScene` (`windows(in:)`) or, on the app-delegate path, the app delegate's window, never from whichever scene is `foregroundActive` at that moment: by `sceneWillResignActive` the scene may already have left that state (no overlay at all), and on iPad multi-window another scene may still hold it (wrong window covered). Each window's cover is one overlay view per host from `overlayHosts(in:)`: the root view controller's view plus the view of every view controller presented above it (share sheet, image picker, alert, full-screen or sheet modal), since an overlay on the root view alone sat under any presented screen and left it live in the App Switcher. Overlays are tracked per window (`NSMapTable`, weak window keys, an array of overlay views each), so each scene is covered and uncovered independently, and the capture-protection secure field is only switched off when the overlay covers the window it protects (`attachedWindow`). iOS's `blur`/`imageBlur` modes render the blur with a synchronous `UIVisualEffectView`/`UIBlurEffect` (selected from the Dart-facing `BlurIntensity` enum — `ultraLight`/`light`/`medium`/`heavy`, default `ultraLight` — via a pure `blurStyle(forIntensity:)` mapping into `.systemUltraThinMaterial`/`.systemThinMaterial`/`.systemMaterial`/`.systemThickMaterial` respectively), attached in the same synchronous step as `color`/`image` mode's overlay — not a manually-captured-and-`CIGaussianBlur`-processed bitmap, which was the original approach. That bitmap approach required the actual blur computation to happen asynchronously off the main thread, meaning the blurred replacement content could attach to the window *after* `willResignActive`/`sceneWillResignActive` had already returned — the same point at which the OS can capture the App Switcher snapshot — creating a race where the snapshot could be taken before the overlay was in place. `UIVisualEffectView` sidesteps this because it attaches synchronously like the other three modes, with no async round trip to race against. `BlurIntensity` replaced an earlier continuous `blurRadius: double` parameter that a pure `blurStyle(forRadius:)` function bucketed into the same styles by radius range, deliberately excluding `.systemThickMaterial`: Apple's thicker/more-opaque materials are designed for toolbars/sidebars needing solid text legibility (confirmed via on-device testing), so on an auto-scaled continuum that tier read as a near-flat, barely-blurred regression rather than the strongest step. Once blur intensity became a discrete, developer-chosen enum instead of an implicit radius bucket, that ambiguity disappeared — `heavy`/`.systemThickMaterial` is now a legitimate, deliberately-selected top tier, so all four materials are exposed. `BlurIntensity`'s value names are deliberately platform-neutral (not `UIBlurEffect.Style` names) so a future Android blur implementation could reuse the same enum. On Android, there is no custom overlay at all: `enableAppSwitcherProtection` simply forces `WindowManager.LayoutParams.FLAG_SECURE` on for the Activity's window and leaves it on for the entire time protection is enabled (mirroring `enableCaptureProtection`'s own flag, and reapplied on Activity recreation alongside it), regardless of which `AppSwitcherProtectionMode` was requested. `blurIntensity` is ignored on Android. **Card colour (Android 13+ / API 33+):** while `FLAG_SECURE` is on, Android shows a blank App Switcher card filled with the task's background colour, which by default is the Activity theme's `android:colorBackground` read once at Activity start (not `windowBackground`, verified on the API 37 emulator), so it ignored the requested colour and, with Flutter's default `configChanges="...uiMode"`, kept the old colour after a dark/light switch until the app restarted. The plugin now sets it itself with `setTaskDescription(TaskDescription.Builder().setBackgroundColor(...))` in `updateTaskBackgroundColor()`: `color` for `color` mode, `imageBackgroundColor` for `image` mode, otherwise (blur modes, or capture protection alone) the theme's *current* `colorBackground`, chosen by the pure `appSwitcherCardColor` (unit-tested; made opaque because `TaskDescription` rejects a translucent background; 0 = no override). It keeps the task's current label and primary/status/navigation-bar colours (Flutter sets those from `MaterialApp.title`/`color` and resets the whole description whenever its `Title` widget rebuilds), so it re-applies on every `onActivityPaused` and `onConfigurationChanged` (callbacks registered per Activity in the `ActivityAware` hooks), and once on enable/disable; after protection is off it resets the background to 0 once. Gated by `isTaskBackgroundColorSupported(sdkInt)`; below API 33 nothing changes. Verified on the API 37 and API 33 emulators (color/image colours, live dark/light switch, off, capture-only). Use `adb emu screenrecord screenshot <abs path>` to see the real card: `adb shell screencap` blacks out secure content, so it always shows black. This design followed direct testing (confirmed on a real device, Samsung SM-J810Y, Android 10/API 29, gesture nav enabled) that established two things: (1) a genuinely-backgrounded task's cached recents snapshot only reflects view content whose final state is set *synchronously*, before/at the first render after pause — meaning a custom overlay view can look right for the settled/discrete case, but any asynchronous or live-compositor rendering (a `RenderEffect` blur, or a `PixelCopy`-captured-and-blurred bitmap) reliably does **not** make it into that snapshot; and (2) **no technique at all** — custom overlay, `RenderEffect`, `PixelCopy`, or even `FLAG_SECURE` itself — hides content during the live "swipe up and hold" gesture-nav peek specifically, because during that hold Android/OneUI's "live tile" recents preview composites the app's actual on-screen window directly (most likely mirroring `FlutterSurfaceView`'s own SurfaceFlinger layer), which is real-time primary-display rendering rather than a capture/cast/recording. Since `FLAG_SECURE` alone already covers everything Android *can* protect (the settled/discrete case — verified via adb across full backgrounding, a direct app-switch peek, and revisiting a cached thumbnail after switching to a different app) and nothing closes the live-hold-peek gap, the custom overlay/blur machinery was removed as pure added complexity with no corresponding protection benefit. **This live-hold-peek gap remains an unfixed, known Android limitation** — no app-level fix exists for it. iOS is unaffected (its secure-window mechanism has no equivalent live-compositor bypass) and keeps its full set of custom overlay `AppSwitcherProtectionMode` renderings.
- **Screenshot detection** (`screenshotEvents`, a `Stream<ScreenshotEvent>`) — reports screenshots as they happen. Backed by the Pigeon event channel `SecureScreenPrivacyEventApi.screenshotEvents` (its own channel, separate from the host API); subscribing to the stream is what starts native detection and cancelling stops it (no separate start/stop method), via the generated `ScreenshotEventsStreamHandler` `onListen`/`onCancel` pair, subclassed by a dedicated handler object on each platform (an anonymous object on Android, `ScreenshotStreamHandler` on iOS, both forwarding to the plugin). Payload is timestamp-only (the detection time on every path; below API 34 not `DATE_ADDED`, which is whole seconds), no file path — deliberately, so no Android storage/media permission is ever requested, and because iOS's notification never carries a path anyway. The plugin's `AndroidManifest.xml` declares only `DETECT_SCREEN_CAPTURE`, an install-time ("normal") permission that is never shown to the user and is not storage/media. **Android has two paths**, picked by the pure top-level function `screenshotDetectionPathForSdkInt`. **API 34+** uses `Activity.registerScreenCaptureCallback` (needs `DETECT_SCREEN_CAPTURE`): exactly one callback per screenshot, only while this app's Activity is visible. It still fires when `FLAG_SECURE` is set (the saved image is black); seen on API 34 and 37 emulators, and the MediaStore path below API 34 reports it too (API 33 emulator), so on Android a blocked screenshot attempt is always reported. It's Activity-scoped, so an `isScreenshotListening` flag threads it through the `ActivityAware` callbacks the same way `screenRecordingEvents` does (register on attach/reattach, unregister before `activity = null` on detach). Registration catches `SecurityException` in case a host app strips the permission from its merged manifest. **Below API 34**, a `ContentObserver` watches `MediaStore.Images.Media.EXTERNAL_CONTENT_URI` (registered against the engine-scoped `appContext`, not tied to Activity attach state, since a screenshot is a device-level event); its `onChange` runs on a dedicated `HandlerThread` and best-effort queries `DISPLAY_NAME`/`RELATIVE_PATH` (or `DATA` pre-API 29) plus `DATE_ADDED`, then feeds them to the pure top-level function `shouldEmitScreenshotEvent` to decide whether to emit — this is a deliberate improvement over the sibling `no_screenshot` plugin, which treats *any* `MediaStore.Images` change as a screenshot with no filtering at all. The filter matches on a "screenshot" substring in the path/name plus recency, but **fails open** (still emits) whenever the metadata is inconclusive (query failed, columns unavailable) rather than silently dropping a real screenshot — a missed screenshot defeats the point of the feature, while an occasional false positive (e.g. a saved photo) does not. This means the filter can both under-report (non-English locales where the display name is localized, e.g. "Bildschirmfoto") and over-report (inconclusive metadata) depending on locale/OEM — not confirmed across real hardware/OEM variance. Without a media permission the query usually returns no rows, so on its own the filter fails open for every MediaStore change. Two framework-free helpers cut that down. `isMediaStoreChangeWorthChecking(flags)` skips `NOTIFY_DELETE` changes, using the API 30+ `onChange(selfChange, uris, flags)` overload. `ScreenshotEventDeduper` (1.5 s window measured from the last emit, reset on each register) collapses the burst one screenshot produces (a pending insert, then an update once written) into one event. Other apps' fresh image inserts below API 34 can still be reported; that's unavoidable without a media permission. On iOS, `UIApplication.userDidTakeScreenshotNotification` is observed via `NotificationCenter`; delivery to `FlutterEventSink` is wrapped in `DispatchQueue.main.async` defensively since Apple doesn't document that notification as guaranteed main-thread. iOS can post that notification more than once for one screenshot (seen on an iPhone 17 Pro, iOS 27.2.1: twice, 3 ms apart, to a single observer), so the internal `ScreenshotEventDeduper` drops any repeat within 0.5 s of the last reported screenshot (monotonic `systemUptime`, reset on each `onListen`); it's unit-tested in `RunnerTests`. Scope differs by path: Android API 34+ only reports screenshots of this app's visible Activity. Below API 34 the `ContentObserver` only runs while the plugin's Activity is started: `updateScreenshotObserver()` registers it when subscribed *and* `isActivityStarted`, and unregisters it otherwise. `isActivityStarted` comes from `Application.ActivityLifecycleCallbacks` filtered to the plugin's Activity (`onActivityStarted`/`onActivityStopped`), seeded on attach from the process importance (pure `isOnScreenImportance`, unit-tested: `IMPORTANCE_FOREGROUND` or `IMPORTANCE_VISIBLE`). It used to run while the app was in the background and reported screenshots of other apps (and any new image); a delivery-time check alone didn't fix that on the API 33 emulator, because Android freezes a cached app and delivers the queued changes when it returns to the front, so they arrived looking like on-screen screenshots. Unregistering on stop means nothing is queued. Within that, it is MediaStore-wide (any screenshot, or any fresh image insert, while on screen). iOS posts the notification to every running app, including one kept running in the background, so `handleScreenshotTaken` drops it unless `appOnScreenProvider()` (default `isAppOnScreen()`: some `.windowApplication` scene is `foregroundActive` or `foregroundInactive`, else `applicationState != .background`) says the app is on screen; the check runs before the deduper so a dropped notification doesn't open its window. The `ContentObserver`/`HandlerThread` and `ScreenCaptureCallback` registration wiring is example-app-verified only (see below); `screenshotDetectionPathForSdkInt`, `ScreenshotEventDeduper` and `isMediaStoreChangeWorthChecking` are unit-tested. The `ContentObserver`/`HandlerThread` wiring itself (as opposed to the pure `shouldEmitScreenshotEvent` filter) is not covered by this repo's Android unit tests — this project's plain-JUnit setup runs against the stub `android.jar` with no Robolectric, where real framework calls like `MediaStore.Images.Media.EXTERNAL_CONTENT_URI` (which touches `Uri.parse` internally) or constructing a real `Looper`/`HandlerThread` throw/misbehave rather than doing anything, so that wiring is manual/example-app-verified only, the same class of gap already accepted for the screen-recording-callback registration wiring below.
- **Screen recording detection** (`screenRecordingEvents`, a `Stream<ScreenRecordingEvent>`) — reports screen recording/mirroring start and stop. Backed by its own Pigeon event channel, `SecureScreenPrivacyEventApi.screenRecordingEvents`, subscribe-starts/cancel-stops just like `screenshotEvents`. **Architectural difference from the < API 34 `screenshotEvents` path**: the Android detection API is Activity-scoped (`act.windowManager`/`act.mainExecutor` need a live `Activity`), unlike the engine-scoped screenshot `ContentObserver` — so this feature threads an `isRecordingListening` flag (set in `onListen`/cleared in `onCancel`, not a separate method call) through the existing `ActivityAware` callbacks: `onAttachedToActivity`/`onReattachedToActivityForConfigChanges` (re-)register against the newly-attached Activity if the flag is set, `onDetachedFromActivityForConfigChanges`/`onDetachedFromActivity` unconditionally unregister (before `activity = null`, since the unregister path reads `activity` itself), mirroring the sibling `no_screenshot` plugin's own `isRecordingListening`-gated pattern exactly. Android has two SDK-gated tiers, selected by the pure top-level function `screenRecordingRegistrationPathForSdkInt`: **API 35+** uses `WindowManager.addScreenRecordingCallback(Executor, Consumer<Int>)`, giving true start *and* stop detection (state compared against `WindowManager.SCREEN_RECORDING_STATE_VISIBLE` via the pure `isRecordingStateVisible`) — its return value also synchronously reports the *current* state, so a late subscriber isn't left waiting for the next transition. It needs the install-time `DETECT_SCREEN_RECORDING` permission, declared in the plugin's `AndroidManifest.xml`; without it `addScreenRecordingCallback` throws `SecurityException` and the stream errors (confirmed on an API 37 emulator before the permission was added), so registration catches it in case a host app strips the permission. **Below API 35**: nothing to register; `onListen` sends one event with `isRecording: null` (Dart maps it to `ScreenRecordingState.unknown`) and nothing after. It's sent from `onListen`, not the `ActivityAware` path, so Activity recreation doesn't repeat it. The API 35+ `SecurityException` path (host app stripped `DETECT_SCREEN_RECORDING`) also sends `unknown`. On the Dart side `ScreenRecordingEvent` carries a `ScreenRecordingState` (`recording`/`notRecording`/`unknown`), and `isRecording` is a getter that's true only for `recording`; the channel payload stays `{isRecording: bool?, timestamp}`, with null meaning unknown. Android 14 has no screen-recording signal: an earlier version used `Activity.registerScreenCaptureCallback` on API 34, but that callback fires for *screenshots*, so it reported every screenshot as "recording started" and never saw a real recording. It's used for `screenshotEvents` instead; minSdk stays 24 (this is purely a runtime `Build.VERSION.SDK_INT` guard). On iOS, `UIScreen.capturedDidChangeNotification` is observed via `NotificationCenter`; because `.isCaptured` is a live boolean re-read on every firing rather than a directional event, one observer correctly reports both start and stop — reads `recordingCheckScene()?.screen.isCaptured`: the scene of this engine's own window (`ownWindowProvider`, same as capture protection), then the active window's scene, then an app-window scene (`.windowApplication` role: active, inactive, then any), then any scene. It used the active scene's key window, which on iPad multi-window can be another window of the app (on another screen with Stage Manager and an external display) and is nil while the app is inactive (Control Center open to start a recording), and then fell back to the first connected scene, which could be an external-display scene. `recordingCheckScene()` is unit-tested in `RunnerTests`. Don't create a `UIWindow(frame:)` without a scene in `RunnerTests`: with parallel testing it made `testEnableCaptureProtection_withoutOwnWindow_fallsBackToActiveWindow` flaky. Both platforms send a state only when it changes, through a small `ScreenRecordingStateDeduper` (reset in `onListen`, so a new subscriber always gets the current state first; unit-tested on both): without it, Android re-sent the current state after every Activity recreation (the API 35+ callback is re-registered and reports it again), and iOS could repeat it when `capturedDidChangeNotification` posts without `isCaptured` changing. On iOS the check runs inside the `DispatchQueue.main.async` block, so the deduper is only touched on the main queue. Neither platform requires a runtime permission. **Reusable pattern worth noting for any future third stream feature**: a single `EventChannel.StreamHandler`/`FlutterStreamHandler` instance registered against two different channels cannot tell which channel invoked `onListen`/`onCancel` (`arguments` is only the Dart-side `listen()` payload, never the channel name) — so this channel gets its *own* dedicated handler rather than reusing the plugin class's existing screenshot handler: an anonymous `object : EventChannel.StreamHandler` on Android (closes over the outer instance for free), and a small dedicated `ScreenRecordingStreamHandler: NSObject, FlutterStreamHandler` class on iOS (holding a `weak var plugin` back-reference, with the plugin itself holding the strong reference so its lifetime is explicit).

Expect to touch all three layers (Dart API, Android, iOS) in tandem when adding to either feature, and update this Architecture section when adding a new one.

## Architecture

Standard Flutter federated-plugin layout, split into a platform-agnostic Dart API and per-platform native implementations connected by [Pigeon](https://pub.dev/packages/pigeon) (moved from the old MethodChannel template to the Flutter 3.50.1 Pigeon plugin template in 0.1.0):

- `pigeon/messages.dart` — the single source of the Dart/native interface: `SecureScreenPrivacyPluginApi` (`@HostApi`, all seven method calls, with typed `AppSwitcherOptionsMessage` and the `AppSwitcherModeMessage`/`BlurIntensityMessage` enums) and `SecureScreenPrivacyEventApi` (`@EventChannelApi`, `screenshotEvents` and `screenRecordingEvents`, carrying `ScreenshotEventMessage`/`ScreenRecordingEventMessage` with `timestampMillis`, `isRecording` nullable for unknown). `dart run pigeon --input pigeon/messages.dart` then `dart format lib/src/messages.g.dart` regenerates `lib/src/messages.g.dart`, `android/.../Messages.g.kt` and `ios/.../Messages.g.swift`; never edit those by hand. `pigeon` is pinned to an exact version in `pubspec.yaml` because CI regenerates and fails on any diff; the `min-sdk` job removes it first (it needs a newer Dart than Flutter 3.38). `pigeon/` is in `.pubignore`, the generated files are skipped by cspell and Codecov (`codecov.yml`). Native code keeps the mode/intensity *names* (`"color"`, `"imageBlur"`, ...) internally via `appSwitcherModeName` (Kotlin) and `modeName`/`blurIntensityName` (Swift), unit-tested against the Dart names.

- `lib/secure_screen_privacy.dart` — public Dart API that app code calls; delegates to `SecureScreenPrivacyPlatform.instance`. Exports `AppSwitcherProtectionMode` (`lib/app_switcher_protection_mode.dart`), `BlurIntensity` (`lib/blur_intensity.dart`), `ScreenshotEvent` (`lib/screenshot_event.dart`), and `ScreenRecordingEvent` (`lib/screen_recording_event.dart`) so a single import is enough.
- `lib/secure_screen_privacy_platform_interface.dart` — abstract `PlatformInterface` defining the contract all platform implementations must satisfy. Uses the `PlatformInterface` token pattern to prevent invalid overrides — any new platform implementation must extend this class and call `PlatformInterface.verifyToken`.
- `lib/secure_screen_privacy_pigeon.dart` — default implementation, `PigeonSecureScreenPrivacy`, calling the generated host API (injectable via `api:` for tests) and mapping the public enums/events to and from the Pigeon messages; this is what `platform_interface.dart` uses unless overridden. Its two streams are built once and cached (`late final`): each call to the generated `screenshotEvents()`/`screenRecordingEvents()` creates a new `EventChannel`, and a second one would take the native handler from the first listener. On unsupported platforms host calls throw `PlatformException(code: 'channel-error')` (it was `MissingPluginException` with the MethodChannel).
- `android/src/main/kotlin/.../SecureScreenPrivacyPlugin.kt` — Android side, registered via `FlutterPlugin`; implements the generated `SecureScreenPrivacyPluginApi` (set up with `SecureScreenPrivacyPluginApi.setUp` on attach, `null` on detach). Its own protection state is `captureProtectionOn`/`appSwitcherProtectionOn` (the `is...Enabled()` names are the API methods). App switcher protection has no rendering of its own on this platform — `enableAppSwitcherProtection`/`disableAppSwitcherProtection` just toggle `WindowManager.LayoutParams.FLAG_SECURE` on the Activity's window, sharing the same reapply-on-Activity-recreation logic as `enableCaptureProtection`'s own flag (see the App switcher protection bullet above for why Android has no custom overlay). The screenshot-event stream uses a dedicated `ScreenshotEventsStreamHandler` object (`screenshotStreamHandler`) — see the "Screenshot detection" bullet above for `onListen`/`onCancel`, the `ContentObserver`, and the `shouldEmitScreenshotEvent` filter. The screen-recording-event stream gets its own `ScreenRecordingEventsStreamHandler` object (`screenRecordingStreamHandler`), both registered in `onAttachedToEngine`, plus `isRecordingListening`-gated (re-)registration wired through the `ActivityAware` callbacks — see the "Screen recording detection" bullet above.
- `ios/secure_screen_privacy/Sources/secure_screen_privacy/SecureScreenPrivacyPlugin.swift` — iOS side (Swift Package Manager plugin layout, not CocoaPods-only; iOS 15.0 minimum since 0.1.0), registered via `FlutterPlugin`; conforms to the generated `SecureScreenPrivacyPluginApi` (`SecureScreenPrivacyPluginApiSetup.setUp`). Its own protection state is `captureProtectionOn`/`appSwitcherProtectionOn`. Image mode loads `UIImage(named: "SecureScreenPrivacyImage")` from the host app's asset catalog, via the internal `appSwitcherImageProvider` closure (swapped out in `RunnerTests`). A missing asset doesn't refuse the call (it used to return `false`, which left the App Switcher showing live content because `SecureScreenPrivacyNavigatorObserver` ignores the result): `enableAppSwitcherProtection` logs a warning and returns `true`, and `makeOverlayView` falls back to a plain `imageBackgroundColor` view (`image`) or a plain blur (`imageBlur`). The two streams are handled by `ScreenshotStreamHandler` and `ScreenRecordingStreamHandler` at the bottom of this file, subclasses of the generated Pigeon handlers that forward to the plugin's `handleScreenshotListen`/`handleScreenshotCancel` and `handleRecordingListen`/`handleRecordingCancel` (the test seam; the plugin keeps strong references to both). Screenshots observe `UIApplication.userDidTakeScreenshotNotification` — see the "Screenshot detection" bullet above.
- `example/` — standalone Flutter app depending on the plugin via a `path: ../` dependency; used both for manual testing (`flutter run`) and integration tests.
- `lib/secure_route_config.dart` + `lib/secure_screen_privacy_navigator_observer.dart` — pure-Dart convenience layer built entirely on top of the public API above (`SecureScreenPrivacyNavigatorObserver` calls `enableCaptureProtection`/`enableAppSwitcherProtection`/etc. per route); no native code involved, so changes here never touch Android/iOS. Popup routes (dialogs, menus, dropdowns: anything not a `PageRoute`) are ignored unless their route name has an entry in `policies` (opt-in, so an app can protect a named dialog or bottom sheet; `defaultConfig` never applies to popups). The observer keeps its own list of the routes it tracks (pages plus those opted-in popups), so when a pop/remove reveals an ignored popup (e.g. a page pushed from a dialog is popped), it applies the policy of the top-most tracked route under it instead of falling back to `defaultConfig`. A route `didPush` reports that isn't the navigator's current route (a page added below the top, e.g. `Navigator.pages` changing from [A, B] to [A, C, B], auto_route's `insert`, or every page but the last when a page list or deep link first builds) is only recorded in that list, just above `previousRoute`, and its policy isn't applied, since what shows hasn't changed. Checked with go_router 18 and auto_route 11 in a scratch app (auto_route `insert` used to apply the inserted page's policy). **Nested navigators:** every observer registers itself in a static weak list and all of them share one static call queue (`_pending`, restarted in the caller's zone when empty so a test's fake-async zone never stalls it). Each step merges the calling observer's config (taken at call time, so quick navigations keep their order) with the current config of every other *showing* observer (read when the step runs): capture protection if any wants it, app switcher settings from the deepest one with a mode. An observer is showing if its navigator is mounted and, when the parent navigator has an observer too, the nested navigator sits inside that parent's top `PageRoute` (`subtreeContext`, found by walking ancestor elements, no inherited-widget dependency) and the parent is showing. Kept-alive tabs all count (over-protects, never under-protects).

When adding a new plugin method: add it to `SecureScreenPrivacyPluginApi` in `pigeon/messages.dart` and regenerate, add it to the abstract platform interface, `PigeonSecureScreenPrivacy` and the public API, then implement the generated interface method in the Kotlin and Swift plugins (the channel names come from Pigeon, so there are no hand-written strings to keep in sync). For a push-based (stream) feature instead of a request/response method, add a method to `SecureScreenPrivacyEventApi` (Pigeon gives each its own event channel) rather than overloading the host API — `onListen`/`onCancel` on its generated stream handler starts/stops the native work, so there's no separate start/stop method call needed. **Every stream gets its own dedicated handler object**: a single handler instance registered against two channels cannot tell which channel invoked `onListen`/`onCancel`, so sharing one is incorrect, not just untidy (and the generated handlers are classes, so the plugin can't be one itself).

Test coverage mirrors this structure: `test/secure_screen_privacy_test.dart` tests the public Dart API against a mock `SecureScreenPrivacyPlatform`, `test/secure_screen_privacy_pigeon_test.dart` tests `PigeonSecureScreenPrivacy` against a fake host API and mocks the Pigeon event channels with `setMockStreamHandler` (`pigeonMethodCodec`), `android/src/test/kotlin/.../SecureScreenPrivacyPluginTest.kt` tests the Android host API implementation directly, and `example/ios/RunnerTests/RunnerTests.swift` (XCTest, hosted in the example app; run with `cd example/ios && xcodebuild test -workspace Runner.xcworkspace -scheme Runner -destination 'platform=iOS Simulator,name=<device>' -only-testing:RunnerTests` after a `flutter build ios --simulator`) tests the iOS app switcher overlay wiring against the host app's real scene. Where native logic depends on real Android framework behavior this plain-JUnit setup can't safely exercise (no Robolectric) — e.g. `MediaStore`/`Uri`/`Looper` for screenshot detection, `WindowManager`/`Activity` screen-recording-callback registration — extract the decision logic into a pure, Android-framework-free top-level function (see `shouldEmitScreenshotEvent`, `screenRecordingRegistrationPathForSdkInt`, `isRecordingStateVisible`) and unit-test that directly instead; the actual registration/callback wiring for all of these is intentionally left to manual/example-app verification only.
